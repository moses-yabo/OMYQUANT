# Installable OMYQUANT web app

OMYQUANT remains the same React Router website. Its web manifest requests a standalone home-screen app with the existing logo and the same origin, routes, authentication and service tools. Installation is optional. It does not create a native APK or an app-store listing.

## Mobile installation

On HTTPS (or localhost), eligible mobile browsers that dispatch `beforeinstallprompt` receive a small install card after four seconds. **Install app** invokes the browser's native installation dialog from that explicit tap. The browser decides whether installation is available and the user confirms it; the site cannot force a download or open that native dialog automatically. Desktop browsers retain their own installation UI.

iPhone/iPad visitors receive instructions to open **Share → Add to Home Screen → Add**, keeping **Open as Web App** enabled if offered. Available menu items depend on the browser and OS. There is no fake iOS native Install button. Already installed standalone windows do not show the card. Dismissing it pauses offers for seven days in that browser; if storage is blocked, dismissal still works for the current visit. Native prompt failures fall back to browser-menu instructions.

The install card sits at the bottom left with device safe-area spacing and follows the current light/dark/system theme, including its buttons and instruction panel. iOS and manual installation guidance uses numbered steps. Buttons and the dismiss control have a minimum 44px touch target; short viewports can scroll the card without changing the page layout.

The root-level controller is mounted after hydration, removes its listeners/timers on cleanup and never requests notification permission. Existing browser notifications retain their separate opt-in and worker. HTTPS is needed on a physical phone; an HTTP LAN address used for local development is not a secure context.

## Apple icon and startup images

Apple home-screen installation has a versioned, explicitly linked opaque 180px RGB icon at `/apple-touch-icon.png?v=3`, plus conventional root-level icon and precomposed fallback files. Existing Android manifest icons are unchanged. Static `apple-touch-startup-image` links are included in the original HTML head for the CSS screen dimensions and pixel ratios listed in `app/lib/apple-startup-sizes.json`, in portrait and landscape. These images reuse the existing logo on the same white background as the Android manifest. They do not change desktop/laptop UI or show an artificial timed loading overlay.

The launch asset matrix currently contains 14 phone screen/scale combinations (28 PNGs). It does not claim coverage for every iPad, display-zoom mode or future device size. Add missing dimensions to the shared JSON and regenerate with `scripts/generate-apple-assets.ps1` using Windows PowerShell/System.Drawing. No extra build dependency is needed. Startup appearance is controlled by iOS before the app runs; the static white artwork does not follow an app-local theme preference.

After deploying, test `/apple-touch-icon.png?v=3` and the matching startup PNG directly in Safari. If an existing home-screen installation still displays the old icon/launch artwork, remove that home-screen web app, revisit the deployed site in Safari, and add it again. Check both launch orientations on the target iPhone. Avoid clearing all site data because that also removes browser demo accounts and saved preferences. Asset/HTTP tests cannot establish iOS OS-level caching or launch behavior on a real phone. Apple's [Safari configuration guide](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/ConfiguringWebApplications/ConfiguringWebApplications.html) documents the Apple icon/startup links and root-level icon discovery.

## Mobile app presentation

At phone widths up to 650px, an installed standalone PWA uses customer bottom tabs for Marketplace, Saved, Activity and Account. Regular mobile browser tabs keep the existing website navigation. Standalone detection uses the display-mode media query with the iOS navigator.standalone fallback, and updates on display changes/page restoration; installing from a browser tab does not change that tab's layout. Activity opens the existing account orders anchor; Account opens the account page or login for guests. The brand/header remains, while duplicate sidebar navigation is hidden only in the installed phone layout. Business and administration workspaces keep their existing navigation and do not receive customer tabs. Desktop and laptop layouts remain unchanged.

Listing dialogs become bottom sheets on phones, with a sticky close control, safe-area spacing, larger form controls and a short entrance animation that respects reduced motion. Native dialog focus containment, Escape/cancel handling and existing booking actions remain in place. The sheet is scrollable; the visual handle does not implement swipe dismissal. Customer support and the install card sit above the bottom tabs. All added surfaces use existing theme variables. Test keyboard, screen-reader, on-screen-keyboard, rotation and back-navigation behavior on actual iOS/Android devices before release; SSR/unit tests do not establish native-device UX.

## Offline and update behavior

`public/sw.js` registers at `/` independently of the notification worker's asset-directory scope. After a successful visit to the unfiltered marketplace (`/` without query parameters), `app/lib/offline-snapshot.ts` saves a static HTML copy of the public marketplace content in the browser's Cache Storage. It clones only `.marketplace-page`, removing scripts, embedded content, event attributes, saved-item buttons, loading overlays and input values. It never clones the account/business navigation, user identity, dialogs or React Router hydration payload. Search and saved-listing views are not persisted. This browser cache is separate from the optional server Redis cache.

The snapshot preserves the existing public content markup and production CSS. Eligible same-origin photos are fetched without credentials so private image responses cannot enter this cache. Downloads are best effort, bounded to 80 photos, 2 MiB per asset and 32 MiB per snapshot; external/oversized/unavailable photos are not stored. The document is committed after its essential CSS and offline guard download successfully, and obsolete assets are pruned. Missing photos may display their alternative text. Local development's injected Vite styles are not an offline production bundle; verify snapshots using the production build.

On network failure at `/`, the worker serves a snapshot saved within the last 24 hours. It is explicitly labelled **Offline copy**, includes a saved timestamp and warns that prices/availability may have changed. The offline copy is static and read-only, without application hydration or a mutation queue. Other pages, missing copies and expired copies use the generic connection page. Nothing guarantees availability before the first successful save/worker activation, and the browser may evict storage. Reload after reconnecting to return to the live app.

`public/offline-client.js` captures offline link clicks (including middle-click), action buttons and form submissions before navigation/action handlers. It cancels the attempted action and opens a themed **You're currently offline** dialog. It allows theme controls and local dismissal controls. A saved static copy remains read-only even when the browser reports online, until explicitly reloaded. OS online/offline signals are hints; loader/API network failures can also signal the controlling page to show the dialog. **Check connection** probes only the public health endpoint and clears a transient failure after a valid response; it never retries the blocked action. An interrupted earlier submission must be checked in account activity before resubmitting. Context-menu browser actions, programmatic code that bypasses DOM events and network loss racing a click cannot be universally prevented by an event guard.

Customer/account pages, API/loader responses, credentials, private documents and authenticated application HTML are never cached. GET loader/API requests retain network-failure semantics, with only a failure signal to the page. POST requests, OAuth callbacks and private document/media navigations are not handled by the worker. Successful navigations and HTTP errors pass through unchanged. Public snapshot CSS, guard assets and eligible image requests use a previously saved copy on network failure. There is no background synchronization or automatic mutation replay.

Cache cleanup removes only obsolete `omyquant-offline-*` caches. Worker updates follow the normal browser lifecycle, without forcing open pages to reload; close existing windows to let a waiting update activate. Increment the offline cache version when changing the offline format or essential assets.

The existing Node static-file server serves the manifest as `application/manifest+json`, the offline page as HTML and the worker as JavaScript. Manifest, offline page and worker responses revalidate; existing hashed asset caching remains intact. The 192/512px app icons and 180px Apple icon are resized copies of the current favicon. No new dependency, hosting configuration or deployment is introduced.

## Verification

Run `npm run typecheck` and `npm test`. Installation-controller tests cover user-gesture prompting, dismissal, installed/insecure/desktop suppression, iOS guidance, cleanup and registration options. Worker tests exercise public snapshot age/path restrictions, cache boundaries, loader failure signals, asset fallback, unchanged HTTP errors and production manifest/icon assets. Offline guard tests cover blocked links/submissions, dialog dismissal, theme controls, static-copy restrictions and connection recovery. These tests use simulated browser events and service-worker APIs; they do not prove real-browser DOM snapshot rendering or OS integration.

Before release, use the production build on localhost or HTTPS and verify these steps on actual devices:

1. Android Chrome/Edge: wait for browser eligibility and the card, tap Install app, confirm, launch the icon and check standalone mode. If dismissed, the custom card should stay hidden for seven days.
2. iPhone/iPad: follow the Share menu instructions and launch from the home screen. The card should be hidden in the installed app.
3. Sign in, navigate business/admin tools as applicable, submit a booking and test existing opt-in notifications without changing account permissions.
4. After the worker activates, visit `/` without filters and wait for the copy/photos to finish saving. Disconnect and reload `/`: the labelled public marketplace copy should appear with its layout and cached photos. Tap a listing, link or submit button: the offline dialog should appear without opening another page or submitting. A private deep link should show only the generic connection page. Inspect Cache Storage to confirm no account identity, private shell or API responses were saved. Repeat with missing/expired snapshots, blocked storage and uncached photos. No interrupted mutation should replay automatically.
5. Reconnect and reload. Verify server-rendered pages and authenticated requests resume normally. Test an update with an existing app window and confirm it becomes active after old windows close.

Browser references: [MDN installation requirements](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable), [MDN install prompting](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/How_to/Trigger_install_prompt), and [Apple home-screen installation](https://support.apple.com/en-kw/guide/iphone/iphea86e5236/27/ios/27).
