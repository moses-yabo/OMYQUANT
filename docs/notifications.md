# Initial browser notifications

Signed-in customers can choose **Enable browser notifications** below the page content. Permission is requested only from that button. Alerts follow successful `/reserve` client actions for farm orders (including livestock), taxi seats and trailer reservation requests, in MongoDB mode and browser demo mode. Failure responses generate no notification. A rental request is not labeled confirmed. Demo alerts explicitly identify browser-only simulated data.

The existing green in-page confirmation remains available when permission is declined, the browser does not support notifications, or notification display fails. Notification failures cannot change a committed order into a failed checkout. Preferences are per browser origin, not a server account subscription. Users can turn alerts off in the app; blocked browser permissions must be changed in site settings. HTTPS or localhost is required. Some mobile browsers require installing the application to the home screen before allowing web notifications; unsupported platforms retain in-page confirmations.

`app/lib/notification-content.ts` defines initial event text and activity links. `web-notifications.ts` manages permission, local opt-in, a per-tab/reference duplicate guard and display. `notification-worker.ts` is TypeScript compiled by Vite using `?worker&url`. It handles notification clicks, allowing only the existing account activity destinations. It does not cache/intercept network requests. Worker registration is performed only after opt-in. The compiled worker uses its own asset-directory scope; page control is not required to show notifications.

These are customer confirmations generated from an open app's successful submission response. They are not provider alerts, a durable notification inbox, cross-device notifications or Web Push after all tabs are closed. The existing Socket.IO browser-room refresh remains unchanged; browser-selected rooms must not carry private server notifications. Direct API clients do not trigger an OS notification on another device.

Later pickup/drop-off alerts should originate from authoritative server status changes, use a persistent notification/outbox record and authenticated recipient routing. Background delivery requires an approved Web Push subscription/VAPID design. Do not generate pickup or delivery events until the domain transition succeeds. No such status alerts, subscriptions, push infrastructure or new dependencies are introduced now.

Verification: test the opt-in button on localhost/HTTPS, allow notifications, and submit one of each listing type. Click each alert to open its activity section. Test denied/default permissions, disabled preference, failed submissions, repeated navigation and a browser without notifications; orders must remain usable. Automated tests cover content/status distinctions, missing references and SSR-safe failure handling. Actual OS permission prompts, mobile behavior and notification clicks need browser verification.

Browser requirements follow the [Notifications API guide](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API) and [service-worker notification API](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/showNotification).
